# S3 compatibility

What TeiFS supports, how it's proven, and where it differs from AWS on purpose. Claims
here come only from tests; nothing is listed as supported because it "should work".

## Operations

| Area | Status |
|---|---|
| ListBuckets, CreateBucket, HeadBucket, DeleteBucket, GetBucketLocation | Supported; ListBuckets pages (`max-buckets`, continuation tokens) and filters (`prefix`, `bucket-region`) |
| GetBucketVersioning | Supported (always "never enabled") |
| PutObject, GetObject, HeadObject, DeleteObject, DeleteObjects, CopyObject | Supported, with ranges, `If-Match`/`If-None-Match`/`If-Modified-Since`/`If-Unmodified-Since` on reads, response header overrides, `COPY`/`REPLACE` metadata directives |
| ListObjects, ListObjectsV2 | Supported: prefix, delimiter, marker/start-after, continuation tokens, max-keys, `fetch-owner`, `encoding-type=url` (encoding the fields S3 encodes in each version) |
| ListObjectVersions, and `versionId` on reads, copies and deletes | Supported for buckets without versioning: each object is its only version, `null`; any other version id is `InvalidArgument` |
| A full disk | `507 XTeiFSStorageFull` (S3 never fills up), before the disk is completely full so deletes keep working, as MinIO's `XMinioStorageFull` |
| Multipart: Create, UploadPart, UploadPartCopy, ListParts, ListMultipartUploads, Complete, Abort | Supported; 5 MiB minimum part size except the last, up to 10,000 parts. Unlike AWS, uploads left unfinished for 7 days are aborted (`--upload-expiry`, or `never`) so abandoned parts don't fill the disk |
| Checksums: Content-MD5, CRC32, CRC32C, CRC64NVME, SHA-1, SHA-256, SHA-512, MD5, XXHASH64/3/128 | Supported, as headers or trailers; stored and returned with `x-amz-checksum-mode`; objects sent without one get CRC64NVME, as on AWS |
| Multipart checksums: `x-amz-checksum-type` `FULL_OBJECT` (CRC32, CRC32C, CRC64NVME, combined from the parts) and `COMPOSITE` (checksum of the parts' checksums, `-N`), checked at Complete; `x-amz-mp-object-size`; a retried Complete answers again | Supported, with AWS's algorithm and type rules |
| Signature V4 (headers, presigned, chunked, trailers); path-style and virtual-hosted-style | Supported. Every `x-amz-*` header a request sends must be signed, presigned links included, so whoever holds a link can't add an ACL, tags, metadata or encryption to it |
| Signature V2 | Refused by default, as AWS does for its newer buckets; `serve --allow-sigv2` accepts it for old clients (a request without a valid `Date` or `x-amz-date` is `403 AccessDenied`, and a whole bucket is signed as `/bucket/`, as on AWS). boto3 makes V2 presigned links unless the client sets `signature_version="s3v4"` |
| Request limits: user metadata (`x-amz-meta-*` names and values) at most 2 KiB, `400 MetadataTooLarge`; a stalled upload body `400 RequestTimeout` | As AWS. Headers are limited to 16 KiB in all (`400 RequestHeaderSectionTooLarge`), more than AWS's 8 KiB for PUT, so long presigned or signed requests still fit |
| Conditional writes on PutObject, CompleteMultipartUpload and CopyObject (`If-None-Match`, `If-Match`) | Supported; atomic on one server. `If-Match` on a missing object is `404 NoSuchKey`, as on AWS |
| Conditional deletes: `If-Match` on DeleteObject, per-object ETag, size and modification time in DeleteObjects, `x-amz-if-match-size` and `x-amz-if-match-last-modified-time` | Supported; deleting a missing object succeeds whatever the condition, as on AWS |
| RenameObject | Supported in both bucket kinds (AWS offers it in directory buckets): source and destination conditions, `x-amz-client-token` idempotency (remembered for a day). A real rename in folder buckets; encrypted objects rename without being re-encrypted |
| GetObjectAttributes (ETag, size, storage class, checksum, parts with pagination); GetObject and HeadObject by part (`partNumber`); HeadObject with `Range` | Supported |
| Object tagging (Put/Get/DeleteObjectTagging, `x-amz-tagging` on PutObject, CopyObject and CreateMultipartUpload, `x-amz-tagging-directive`, `x-amz-tagging-count`) and bucket tagging | Supported, with S3's limits (10 per object, 50 per bucket, key and value lengths, characters); a tag change keeps Last-Modified and the ETag |
| CORS: Put/Get/DeleteBucketCors, preflight `OPTIONS`, `Access-Control-*` on requests with an `Origin` (errors included) | Supported: first matching rule, one `*` in origins and headers, 100 rules |
| Server-side encryption: SSE-S3 (`AES256`), SSE-KMS (`aws:kms`, named keys, encryption context), SSE-C (customer keys) on PutObject, GetObject, HeadObject, CopyObject (source and destination keys), multipart uploads and UploadPartCopy | Supported in object buckets, with AWS's rules: SSE-C only over a secure connection, ETags not MD5 for SSE-KMS and SSE-C |
| KMS | A local keyring, or a Vault/OpenBao transit engine (tested nightly against OpenBao); `teifs key` lists, creates and rotates keys in either |
| Get/Put/DeleteBucketEncryption, including `BlockedEncryptionTypes` | Supported. Object buckets default to SSE-S3 with SSE-C blocked, as AWS buckets do since April 2026 |
| DSSE-KMS (`aws:kms:dsse`), UpdateObjectEncryption, S3 Bucket Keys caching | Not yet (Bucket Key settings are recorded and reported) |
| IAM: users, access keys, groups, roles, OpenID Connect providers, customer-managed policies (five versions), inline policies, attachments, permissions boundaries, user, role, provider and policy tags | Supported with AWS's names, paths, quotas, size limits and error codes. A role's trust policy names principals and `sts:` actions only, never a `Resource`, and is at most 2048 characters; the users and roles of the account it names must exist and are bound to their unique ids, so one deleted and made again under the same name isn't trusted, as on AWS. Every request signed with a user's key is decided by the user's and its groups' policies and boundary, for the bucket, key and copy source the operation acts on |
| The IAM API (Query protocol) on the S3 endpoint: 80 actions, the above (roles: Create/Get/List/Update/UpdateRoleDescription/DeleteRole, UpdateAssumeRolePolicy, their inline and attached policies, tags and boundaries; OpenID Connect providers: Create/Get/List/Delete, Add/RemoveClientID, UpdateThumbprint, their tags) and `GetAccountSummary` | Supported: `aws iam --endpoint-url …` and the SDKs work unchanged. Each action is authorized as on AWS, with its condition keys (`iam:PolicyARN`, `iam:PermissionsBoundary`, `aws:RequestTag`, `aws:TagKeys`, `aws:ResourceTag`, `iam:ResourceTag`) on the entity's own ARN, whatever case a name is given in. OpenID Connect providers keep AWS's limits (100 per account, 100 audiences, 5 thumbprints of 40 hex digits, a URL of at most 255 characters with no query or fragment, one provider per URL); deleting one that doesn't exist succeeds, as on AWS. TeiFS also takes a port in the URL and `http://` for a provider on the same machine (`localhost`, a loopback address), which AWS doesn't. MFA, login profiles, instance profiles, SAML providers, SSH and signing keys are not there; key and role last-use isn't recorded |
| STS: `AssumeRole`, `AssumeRoleWithWebIdentity`, `GetSessionToken`, `GetFederationToken`, `GetCallerIdentity`, `GetAccessKeyInfo` | Supported with AWS's rules and error codes: trust policies decide `AssumeRole` (with `sts:ExternalId`, `sts:RoleSessionName`, `sts:SourceIdentity`, `sts:TransitiveTagKeys`, request and role tags); session policies (inline, and up to 10 managed by ARN) and session tags, packed into at most 6 KiB of token (`PackedPolicyTooLarge`); `SessionTokenUtilization` and `SessionTokenSize` in every answer, and `PackedPolicySize` as before; `MinimumSessionTokenSize` (0 to 4096) on every action that issues credentials pads the token to at least that many bytes, which counts for neither the packed limit nor the utilization; durations as AWS allows them (15 minutes to the role's maximum, an hour for role chains and the root user, up to 36 hours for session tokens and federated users); transitive tags and the source identity kept along role chains; `GetSessionToken`'s and federated users' credentials refused by IAM (`InvalidClientTokenId`) and limited in STS. Temporary credentials sign S3 requests with the token in the `x-amz-security-token` header, a presigned URL's query or a browser upload's form; expired ones get `ExpiredToken`, wrong or missing tokens `InvalidToken`. MinIO's `AssumeRole` (no `RoleArn`, or not an AWS one): the user's own permissions, narrowed by `Policy`, for up to 365 days. Managed session policies (`PolicyArns`) are read when the session starts, so a later new default version doesn't reach sessions already issued (AWS reads them on each request). `AssumeRoleWithWebIdentity` as AWS answers it, unsigned: the token is an OpenID Connect ID token of one of the account's providers (its issuer), signed with RS256/384/512, PS256/384/512 or ES256/384/512 by a key the provider publishes (OpenID Connect Discovery, then its `jwks_uri`), for one of the provider's client ids (`azp`, else `aud`), with `sub` and an unexpired `exp`; `InvalidIdentityToken`, `ExpiredTokenException` and `IDPCommunicationError` as on AWS. The trust policy decides with the provider's keys (`aud`, `oaud`, `sub`, `amr` and every other claim of text, number, boolean or list of text, by the provider's name: `token.actions.githubusercontent.com:repository`), `aws:FederatedProvider`, `sts:RoleAuthorizedByIdp` (from the `https://aws.amazon.com/roles` claim), `sts:RoleSessionName`, session tags from `https://aws.amazon.com/tags` (with `sts:TagSession`) and the source identity from `https://aws.amazon.com/source_identity` (with `sts:SetSourceIdentity`); the session has `aws:FederatedProvider` and the provider's `aud`, `sub` and `amr`. Providers' keys are kept as their `Cache-Control` says (5 minutes to a day, an hour if unsaid), fetched again for a key they don't have (at most every 30 seconds), and used up to a day while a provider can't be reached; the fetch follows no redirects. A provider's certificate is trusted when the system trusts it, as AWS does for well-known authorities; else its thumbprints pin it: a presented certificate with one of them (the top intermediate authority, or a self-signed server) is the chain's only anchor, and the chain, dates and host name are still checked. A trust policy's `Federated` principal that names an OpenID Connect provider of the account must name one that exists (`MalformedPolicyDocument`), as on AWS. `ProviderId` (OAuth 2.0 access tokens of Amazon and Facebook) is refused. MinIO's `AssumeRoleWithWebIdentity` without `RoleArn`, for a provider tagged `teifs:policy-claim` (an empty value means MinIO's `policy` claim, another names the claim): the managed policies the claim names (a list, or text separated by commas; names in any case, or ARNs) that exist, narrowed by `Policy` and `PolicyArns`, for `DurationSeconds` (15 minutes to 365 days) or until the token expires; `InvalidParameterValue` as MinIO answers when the claim is missing or names no policy. The session's `GetCallerIdentity` has no ARN, the user id `provider-arn:sub` and the account. A provider without the tag needs `RoleArn`, as on AWS, and MinIO's role ARNs (`arn:minio:iam:::role/…`) are refused, since TeiFS has no role policies. Not there: MFA (a code is refused), `AssumeRoleWithSAML`, `AssumeRoot`, `DecodeAuthorizationMessage`. Session tokens don't carry over to another drive, since the drive's IAM key seals them |
| Bucket policies: Put/Get/DeleteBucketPolicy, GetBucketPolicyStatus | Supported, with AWS's evaluation: a Deny binds everyone, the root user included, except that the root user can always read, replace and delete the policy; a statement naming a user grants it directly, one naming the account needs the user's own policy too; anonymous requests are decided as `Principal: *` and never manage the policy. Policies are checked when stored (`MalformedPolicy`): at most 20 KB, S3 actions and condition keys only, resources only in the bucket. "Public" is decided as AWS does: an Allow for everyone unless a condition pins fixed values of `aws:SourceIp` (no broader than /8, /32 for IPv6), `aws:SourceVpc(e)`, `aws:SourceArn`, `aws:SourceAccount`, `aws:SourceOwner`, `aws:PrincipalArn`, `aws:PrincipalAccount`, `aws:PrincipalOrgID`, `aws:userid` or `s3:DataAccessPoint*` |
| Block Public Access: Put/Get/DeletePublicAccessBlock on buckets | Supported: all four settings on for every new bucket (and for folders made by hand), as on AWS. `BlockPublicPolicy` refuses a public policy; `RestrictPublicBuckets` makes a public policy grant nothing to anonymous requests, on every operation; `BlockPublicAcls` refuses public ACLs (`AccessDenied`); `IgnorePublicAcls` makes stored ones grant nothing |
| Account-level Block Public Access: S3 Control's Get/Put/DeletePublicAccessBlock | Supported: applies with every bucket's settings, each setting on where either has it, as on AWS; buckets still report only their own. The SDKs and the AWS CLI put the account in the host name (`{account}.endpoint`), so give them an endpoint whose subdomains reach the server: `http://localhost:9000` works on one machine, or a name with wildcard DNS. The account is `aws sts get-caller-identity`'s. Nothing else from S3 Control (`501 NotImplemented`) |
| Object Ownership: Put/Get/DeleteBucketOwnershipControls, `x-amz-object-ownership` on CreateBucket | Supported. New buckets are `BucketOwnerEnforced`, as on AWS: ACLs are disabled, writes with any ACL but `bucket-owner-full-control` fail with `AccessControlListNotSupported`, and reading an ACL answers the owner's full control. ACLs can't be disabled while the bucket's ACL grants others (`InvalidBucketAclWithObjectOwnership`); a bucket with no setting has ACLs, as S3's buckets from before April 2023. `serve --legacy-bucket-defaults` makes new buckets that way (no setting, no Block Public Access) |
| ACLs: Get/PutBucketAcl, Get/PutObjectAcl, canned ACLs and `x-amz-grant-*` on CreateBucket, PutObject, CopyObject and CreateMultipartUpload | Supported where Object Ownership enables them, with AWS's evaluation: an ACL allows what no policy decided (never past an explicit Deny or a permissions boundary), with AWS's mapping of ACL permissions to actions. A drive is one account, so a grant names the owner (`id=teifs`) or a group: everyone (`AllUsers`), every signed request (`AuthenticatedUsers`) or log delivery; other ids are `InvalidArgument`, email addresses `UnresolvableGrantByEmailAddress`. A copy never takes its source's ACL |
| Browser uploads: PostObject (`POST` with a form), signed with Signature V4 (or V2 with `--allow-sigv2`) or anonymous | Supported: the POST policy (expiration, `eq`, `starts-with`, `content-length-range`), `${filename}`, `acl`, `tagging` (a tag set, as XML), metadata and the other object headers as fields, `success_action_status` and `success_action_redirect` with the quoted ETag. The upload is authorized like PutObject on the key the form names, with `s3:authType` `POST`. As on AWS, every field must be named by a condition of the policy, checksum fields included, and a failed condition is `403 AccessDenied`. The fields before the file may take at most 64 KiB (`400 MaxPostPreDataLengthExceeded`) |
| Upload size caps (a TeiFS addition, as RustFS has): `x-teifs-max-content-length=N` in a Signature V4 signed PutObject's query (a presigned link's, typically) caps its body at N bytes; `x-teifs-max-total-object-size=N` on CreateMultipartUpload caps the upload's parts, all together, including copied parts and parts sent again | Supported. The signature covers the query, so a cap can't be raised or removed. A larger body is `400 EntityTooLarge` before it's stored, one of unknown length `411 MissingContentLength`. A cap on an unsigned or Signature V2 request, on any other operation, given twice, spelled otherwise or not a whole number is `400 InvalidRequest` rather than ignored. `teifs presign --put --max-size` makes such links. Other S3 clients ignore the parameters they don't sign |
| Versioning, Object Lock, lifecycle | Planned |
| Notifications, website hosting, logging, replication | Planned |
| S3 Select, Glacier restore, torrents, Object Lambda, accelerate | Not planned for now |

## Bucket layouts

A bucket is either an **object bucket** (the default: objects stored by id, every key S3
allows, encrypted at rest) or a **folder bucket** (a folder of plain files). Choose when
creating it: the `x-teifs-bucket-layout: object|folder` header on CreateBucket, `teifs
bucket create --layout`, or the server's `--default-layout`. The differences below apply to folder
buckets only; object buckets have none of them. Folder buckets also can't be encrypted:
their objects are plain files by design.

## Differences from AWS in folder buckets, by design

Storing objects as plain files means some keys can't exist, the same way other S3 servers
that map keys to paths behave:

| Behaviour | TeiFS | AWS |
|---|---|---|
| Key with `.` or `..` segments, an empty segment (`a//b`) or a leading `/` | `400 InvalidArgument` | Accepted |
| Keys `a` and `a/b` at once | The second: `409 XTeiFSKeyConflict` | Both accepted |
| Keys differing only in letter case, on a case-insensitive disk | The second: `409 XTeiFSKeyConflict` | Both accepted |
| Keys differing only in Unicode form (`é` composed or decomposed), on a disk that treats them as one name (APFS, HFS+) | The second: `409 XTeiFSKeyConflict` | Both accepted |
| Names Windows can't hold: device names (`CON`, `NUL.txt`, `COM1`, `LPT1`, …), any of `<>:"\|?*`, control characters, a segment ending in `.` or a space | `400 InvalidArgument` on every system, so the drive can move between them; `serve --key-names host` allows them except on Windows. Such files put there by other programs are still listed, read and deleted | Accepted |
| Folder bucket named after a Windows device (`con`, `nul`, `aux`, `prn`, `com1`, …) | `400 InvalidBucketName` | Accepted |
| A key ending in `/` with content | `400 InvalidRequest` (it's a folder) | Accepted |
| ETag of a file changed outside TeiFS | Provisional `<hex>-1` until the background indexer hashes it (within one pass, 30 minutes apart) | Always the MD5 |

Use an object bucket for data that needs these keys.
